# Контекст для фронтенда url-shortener

Этот файл — бриф для новой сессии Claude, которая будет поднимать фронтенд (Next.js). Бэкенд (Go) живёт в этом же репозитории, `internal/`.

## Что это за продукт

Укорачиватель ссылок: создание короткого кода, редирект, трекинг кликов (страна/город по IP), статистика по ссылкам для залогиненного пользователя (Google OAuth). В планах — платные подписки на аналитику (см. "Планы" ниже).

## Топология (локально)

- **Caddy — единственная точка входа**, слушает `:80` на хосте, всё остальное (Postgres/Redis/Redpanda/сам Go-бэкенд) сидит только во внутренней docker-сети, наружу не торчит.
- Локально бэкенд доступен только как `http://localhost` (порт 80, через Caddy). Порт `5050` — это порт Go-процесса *внутри* docker-сети, с хоста напрямую недоступен.
- Если бэкенд поднят не в докере, а через `make run` — тогда `http://localhost:5050` напрямую, без Caddy.
- Фронтенд предполагается **отдельным dev-сервером** (Next.js на своём порту, например `:3000`) — значит нужен CORS между `localhost:3000` и `localhost` (см. "Что нужно поправить в бэкенде" ниже).

## Версионирование API

Всё под `/api/v1/...`, **кроме** самого редиректа по короткой ссылке — `GET /{code}` сознательно без версии, это и есть продукт (короткая ссылка не должна тащить на себе `/api/v1`).

## Роуты

| Метод | Путь | Auth | Тело запроса | Ответ | Примечание |
|---|---|---|---|---|---|
| `POST` | `/api/v1/link` | опционально (см. ниже) | `{"url": "https://..."}` | `201` `{"short_code": "...", "original_url": "...", "user_id": "...\|null"}` | Если юзер залогинен (кука сессии валидна) — ссылка привязывается к нему (`user_id` не null), иначе анонимная |
| `GET` | `/{code}` | нет | — | `302` редирект, либо `404` | **Без версии.** Не вызывается фронтом через fetch — это то, на что реально переходит конечный пользователь по короткой ссылке |
| `GET` | `/api/v1/auth/google/login` | нет | — | `302` на Google | **Не fetch, а полноценная навигация браузера** (`window.location.href = ...` или `<a href>`), не AJAX — иначе не сработает |
| `GET` | `/api/v1/auth/google/callback` | нет | — | `302` на `AUTH_SUCCESS_REDIRECT_URL` | Google сам сюда редиректит, фронт эту ручку никогда не вызывает напрямую |
| `POST` | `/api/v1/auth/logout` | да | — | `302` на `/` | — |
| `GET` | `/api/v1/clicks?limit=&offset=` | да | — | `200` `{"items":[{"short_code":"...","click_count":N}], "total":N}` | `limit` default 10, max 100; `offset` default 0. Требует сессию, иначе `401 unauthenticated` |

## Аутентификация — как это работает с фронта

Это **cookie-based сессия через серверный OAuth-флоу (BFF-паттерн)**, не access/refresh токены в JS:

1. Кнопка "Войти через Google" — это `<a href="{API_BASE}/api/v1/auth/google/login">`, не JS-вызов. Браузер должен реально уйти со страницы.
2. После логина Google редиректит обратно на бэкенд, бэкенд ставит `HttpOnly`-куку сессии и редиректит браузер на `AUTH_SUCCESS_REDIRECT_URL` (сейчас в `.env` бэкенда — `http://localhost:5050/`, **это нужно поменять на адрес фронта**, см. ниже).
3. Дальше все запросы с фронта к `/api/v1/*` должны идти с `credentials: 'include'` (fetch) / `withCredentials: true` (axios) — иначе кука сессии не поедет и бэкенд не увидит юзера.
4. Токена/JWT на руках у фронта никогда не будет — это осознанное решение бэкенда (кука недоступна для JS, защита от XSS).

## Ошибки — единый контракт

Любая ошибка API — JSON вида:
```json
{"code": "not_found", "message": "...", "details": [{"field": "url", "rule": "max", "param": "2048"}]}
```
`details` — только при ошибках валидации, иначе отсутствует. Коды и статусы: `not_found`→404, `invalid_argument`→400, `conflict`→409, `unauthorized`→401, `unauthenticated`→401, `internal_error`→500. Текст `message` можно показывать как есть, `err.Error()` в него никогда не попадает (только в серверный лог).

## Что нужно поправить в бэкенде, когда фронт появится

Это НЕ сделано заранее специально — правится один раз, когда будет реальный адрес фронта:
- `.env`: `HTTP_ALLOWED_ORIGINS` — добавить origin фронта (сейчас там только `http://localhost:5050`, `http://127.0.0.1:5050`), иначе CORS зарубит запросы с `localhost:3000`.
- `.env`: `AUTH_SUCCESS_REDIRECT_URL` — сейчас `http://localhost:5050/` (это бэкенд, там нет роута на `/`, будет 404). Нужно указать реальную страницу фронта, куда пользователь должен попасть после логина.

## Известные пробелы бэкенда (важно для планирования фронта)

- **Нет эндпоинта "мои ссылки" со списком URL.** `/api/v1/clicks` отдаёт только `short_code` + `click_count`, **без `original_url`**. Чтобы построить дашборд "твои ссылки + сколько кликов" с показом оригинального URL, нужна доработка бэкенда (сейчас такого эндпоинта физически нет).
- **Гео (страна/город) собирается, но нигде не отдаётся.** В БД аналитики уже есть `country`/`city` по каждому клику, но ни один HTTP/grpc эндпоинт их не возвращает — разбивка кликов по геолокации на дашборде тоже потребует новой ручки на бэкенде.

## Планы (из README "Что дальше")

- Платные подписки на аналитику — статистика по ссылкам, видна только владельцу (уже частично есть, `/clicks`).
- График кликов по времени.
- Разбивка кликов по странам/городам (данные есть, API — нет, см. выше).

## Как этим пользоваться в новой сессии

Скажи новой Claude-сессии что-то вроде: *"прочитай D:\projects\url-shortener\FRONTEND_CONTEXT.md, дальше поднимаем фронтенд на Next.js"*. Если фронтенд будет жить в подпапке этого же репозитория (`D:\projects\url-shortener\frontend`) — ещё лучше, тогда и этот файл, и `CLAUDE.md` подхватятся автоматически, без необходимости указывать путь руками.
